# Gemini 4 Carbon 关于“有无坏味”和“坏味轻重”的解释复核

**总判断。** 在这批贴近修复位置的注入实验中，从无额外注入到 S0 的平均 token 增量很清楚。从 S0 加到 S2，三类坏味汇总后的平均增量较小，但不同坏味、模型和任务的表现有实质差异。Carbon 提出的局部读取机制有轨迹支持。将整段差异解释为一笔固定的跨模块成本，或把分支数确定为唯一的边际成本来源，证据不足。[Carbon 原文第 3.2 节](../smell_paper/PAPER.md#L93)

## 观察值支持哪部分结论

按同题、同模型配对，先在原题内平均对数比，再给每道原题相同权重。下表的 S2 对 S0 限定同一原题、同一坏味的两档都有有效遥测，区间按仓库重抽样 5,000 次。

| 模型 | S0 对无注入，三类汇总 | S2 对 S0，三类汇总（95% 区间） | 所有注入配对中实际多用 token 的比例 | 单看 Long Method 的 S2 对 S0（95% 区间） |
|---|---:|---:|---:|---:|
| GPT | +6.6% | +2.8%（−0.2% ～ +6.0%） | 58.5% | +7.9%（+3.0% ～ +13.0%） |
| GLM | +25.6% | +6.0%（−0.2% ～ +13.4%） | 64.0% | +13.1%（+3.0% ～ +23.6%） |
| DeepSeek | +26.8% | +3.1%（−2.5% ～ +8.6%） | 67.5% | +5.1%（−4.8% ～ +15.7%） |

“但凡”若指每次修复，都有大量反例。“严重程度影响小”描述的是端点的汇总估计。以 GLM 的 God Class 为例，逐题比较 S1 比 S0 多 13.9%（+2.4% ～ +25.1%，264 题），S2 又比 S1 少 14.8%（−21.7% ～ −6.8%，260 题），而 S2 对 S0 只差 −3.0%（−13.0% ～ +7.6%）。端点接近也可能来自中间档上升后回落。这些相邻档区间用于描述该现象，未作多重校正，运行批次仍可能参与解释。[原文表 3](../smell_paper/PAPER.md#L99) · [原始分档估计](../smell_paper/data/results.json)

论文的 68%、78%、88% 可以复现。其定义为“无注入至 S0 的平均对数增幅”除以“无注入至 S2 的平均对数增幅”。保留两端的相关性，按仓库联合重抽样，该比例的 95% 区间分别为 GPT 19.5% ～ 100.3%、GLM 60.2% ～ 98.3%、DeepSeek 70.5% ～ 109.9%。同样算法用于 GPT 的 Feature Envy 得到 143%，用于 GPT 的 Long Method 则是 36%。这个比例描述两组平均增幅的相对大小，不能用来核算某一笔固定成本或重构最多能节约多少 token。三个档位的补丁分别从原始 base 独立生成。[计算定义](../smell_paper/analysis.py#L81) · [注入起点](../../prompts/S2/LongMethod.md#L74)

如果“结果”指修复成功率，仓内可直接比较的是 GPT。重读测试报告后，S0、S2 均有二元判定的共有 629 对、271 道原题。按题等权，S2 对 S0 的成功率差为 −0.12 个百分点（−3.24 ～ +2.91）。该样本未检出明确变化，GLM、DeepSeek 的成功率仍缺少相应判定。[评测报告目录](../../bench_result)

## 三项机制核查

### 1. 共同注入下限可以解释为什么 S0 就很重

三档均要求坏味处于修复热点或邻近区域，RAD 至少涉及 3 个生产文件、2 个模块，平均结构距离至少 2.0。仅 God Class 的 S0 就已要求 1,000 ～ 2,999 有效 LOC。这样的最轻档已经可能增加检索、阅读和验证成本。无额外注入的对照本身也可能带有既有坏味。[注入模板](../../prompts/S0/GodClass.md#L30)

但相同下限不保证同一任务的结构固定。God Class 各档相关文件数的中位数都是 7，逐题比较 S0 和 S2，263 道有完整记录的任务中，只有 28 道文件数相同。模块数在 264 题中只有 109 道相同。更关键的是，图 3 左侧将无注入组的相关文件数和模块数直接写为 1，代码没有读取对照的静态度量。因而图上的“1 → 7”不能作为首次跨模块直接导致 token 跃升的观测证据。[图 3 绘图代码](../smell_paper/figures.py#L167)

### 2. 局部窗口能削弱体积效应，实际修复位置决定它是否生效

Carbon 对 GPT 的 God Class 统计有说服力。S0、S1、S2 的注入补丁新增行数中位数约为 1,225、3,539、6,023，命中注入所涉文件的读取或检索调用，其每次任务累计返回字符数中位数却是 18.4k、18.8k、18.3k。这个指标包含匹配调用的完整输出，能衡量可观察的阅读量，不能识别其中每一行是否与 issue 有关。对 Long Method，文中的“5.1 倍”特指 GPT **相对对照多读字符**的中位数比值（1,866 → 9,599）。相应注入组的总返回字符中位数是 11,305 → 19,835，约 1.75 倍。[字符统计口径](../smell_paper/structural.py#L203) · [逐调用的匹配规则](measure.py#L232)

窗口可以直接跳到文件深处。核查 262 条 GPT God Class S2 有效轨迹，69 条用结构化 `read` 实际返回了目标文件第 2,000 ～ 6,500 行范围内的源码，62 条在首次可识别改写之前就已读到。Lucene #13494 先搜索，再一次读取第 5,180 ～ 5,699 行。这个检查说明长文件深处的代码有机会进入上下文，无法据此认定其中每个方法都相关或都无关。[实际工具返回](../../traj_results/opencode/gpt/GC-S2/apache__lucene-13494/trajectory.jsonl#L15)

Long Method 也可以对照两条具体轨迹。Lucene #12626 的修复点从方法入口后 2 行移到 291 行，首次修改前的目标文件读取从 1 次增至 5 次。Preact #4316 的方法有 250 LOC、CC 50、8 层嵌套，但修复所需的事件分支就在首次 260 行读取内，仍只读一次就开始改，两侧均通过，token 从 197,059 降至 126,297。**可见性和所需控制流路径**比“长方法每一行都必须读”更贴近这两条记录。[Lucene 最后一次定位读取](../../traj_results/opencode/gpt/LM-S2/apache__lucene-12626/trajectory.jsonl#L21) · [Preact 首次读取](../../traj_results/opencode/gpt/LM-S2/preactjs__preact-4316/trajectory.jsonl#L6)

论文的 160 行分界来自分组比较。180 行是 GPT 无注入组结构化读取中显式请求上限的中位数。对 828 个 GPT 长方法配对，再做一次敏感性检查，同时考虑原题固定效应、注入档位和连续的对数 LOC，另加“超过 160 行”的阶跃项，估计为 +16.8%（−1.9% ～ +38.9%）。数据容许窗口附近存在明显增幅，也容许沿连续规模变化。它不足以确立通用的 160 行硬上限。[原分组](../smell_paper/analysis.py#L174) · [读取上限的计算](../smell_paper/analysis.py#L218)

### 3. 全样本分支图混合了不同坏味，无法识别独立驱动因素

按原脚本规则，从全部 2,424 份注入补丁重新计数。该量是所有新增文本行中的 `if`、`else`、`for`、`case` 等词的出现次数，未扣除移走的旧实现，也未限定在目标方法、待修复路径或可执行语句内。[关键词定义](../smell_paper/structural.py#L14) · [取新增行计数](../smell_paper/structural.py#L24)

| 新增关键词数 | Feature Envy 变体 | God Class 变体 | Long Method 变体 |
|---|---:|---:|---:|
| ≤15 | 592 | 2 | 166 |
| 16–45 | 187 | 4 | 403 |
| 46–150 | 22 | 156 | 262 |
| >150 | 0 | **630** | **0** |

最高一档的 **1,877 个有效模型配对全部来自 God Class**。此外，GPT 四档平均增幅实际为 **5.0%、5.3%、12.3%、10.3%**，论文把第三档的 12.3% 写到了最高档。GLM 从第一档到第二档也有回落，三个模型中仅 DeepSeek 四档连续上升。Long Method 自身的 S2 对 S0 结果支持剂量效应，但不能用上述混合分箱证明“必经分支是唯一驱动因素”。同一原题同一目标方法的 581 对长方法变体中，没有一对只改变 LOC、CC、嵌套深度三项中的一项。[原分箱实现](../smell_paper/structural.py#L126) · [独立指标核查](METRIC_FINDINGS.md#L24)

## 更符合现有证据的表述

在这批注入到修复热点的实验里，最轻注入已经使三个模型的平均 token 消耗上升。继续加重后，新增代码是否进入 Agent 实际要定位、理解或验证的路径，会影响额外开销。局部读取可以跳过部分并列代码，修复点离开原读取窗口时则可能需要多轮定位。不同坏味和模型的剂量响应并不相同，固定的跨模块成本比例、唯一的分支成因以及普适的行数门槛，还需要将这些因素独立操纵并随机交错运行才能验证。

复核脚本读取原补丁、轨迹、评测结果及逐题配对表。运行 `uv run --python 3.12 analysis/smell_impact/audit_carbon.py` 可复算文中的附加检验。本次未重跑模型。[复核脚本](audit_carbon.py)

对“为什么需要多定位、多读和返工”的进一步核对，逐项追踪了失效的旧方法位置、同一关键词增加的命中、移出阅读窗口的状态赋值，以及放宽数组判断后失败的具体断言。[代码变化与工具动作的逐项对照](METRIC_FINDINGS.md#L91)
